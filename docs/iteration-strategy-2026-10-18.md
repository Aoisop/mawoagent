# mawoagent 项目研读、外部对比与迭代方向

研究日期：2026-10-18。基于当前工作区代码与当天访问的官方项目资料、论文。本文是产品与技术判断，不是已经验证的市场需求或模型效果报告。

## 1. 我的判断

**最值得推进的方向，是把 mawoagent 做成一个本地优先、可验证的技能学习与发布工作台：用户纠正一次，系统形成有来源、有适用条件、有执行证据、可以回退的改进。**

现有 Runtime 继续作为参考执行器和实验平台。等学习效果得到证明，再把学习与评测模块开放给其他 Agent 使用。不要一开始同时建设通用编码工具、个人助理平台、多 Agent 编排框架和技能市场。

真正需要证明的产品承诺是：

> 在同一类重复工作中，经过你的纠正，下一次任务需要更少返工；系统能展示改进发生在哪里、代价是多少，以及什么时候不该使用这条经验。

“自进化”可以描述实现机制，但不能代替这个承诺的证据。现阶段更准确的定位是“具备受控技能演化机制的本地 Agent Runtime”，还不足以断言“已经越用越聪明”。

判断置信度：对代码现状、评测缺口和竞争重叠的判断较高；对首批用户与商业场景的判断中等偏低，因为仓库中没有用户访谈、留存、返工率或付费数据。

## 2. 研读范围与项目真实形态

本轮按模块通读了 `agents/` 的 32 个 Python 文件，扫描时共 10,086 行；检查了 Web 前端、运行文档、依赖和 CI，并梳理 18 个测试文件中的 213 个测试方法，对关键评测与故障恢复测试做了重点阅读。核对了参考论文的公开内容，并检查了数据目录及其与评测入口的关系。

没有逐条审读所有 benchmark 样本与第三方文档，也没有把这些第三方数据算作项目自产能力。本轮不调用付费模型，不宣称取得任何真实模型 benchmark 成绩。外部项目对比依据其官方公开资料，不等同于全面审计这些项目源码。

项目目前有四个层次：

| 层次 | 已有实现 | 判断 |
| --- | --- | --- |
| 执行 Runtime | 双协议模型循环、文件与 Shell 工具、权限、子 Agent、MCP | 已构成完整执行闭环；这是必要基础，但同类项目重叠很大 |
| 长任务与上下文 | 工具结果落盘、分层压缩、结构化会话折叠、恢复检查点 | 有实际工程工作，适合作为研究与实验基础 |
| 经验学习 | 用户反馈窗口、抽取、add/merge/discard、候选隔离、来源记录、版本回退 | 是当前最值得继续建设的主线 |
| 产品入口 | CLI、本地 Web、Skills/候选/记忆/评测页 | 已能承载完整体验；评测与审核仍偏开发者工具 |

核心运行代码见 [Agent](D:/mawoagent/mawoagent/agents/agent.py:166)、[工具执行边界](D:/mawoagent/mawoagent/agents/tool_runtime.py:9)、[Web 服务](D:/mawoagent/mawoagent/agents/web.py:418)。

值得保留的工程资产包括：执行时重新检查权限；不执行不完整模型响应中的工具；断流输出回退；工具执行前后持久化；中断后区分“未开始、已完成、结果未知”；大结果先落盘再记录完成；候选正文、基础版本与发布审批绑定。这些机制有明确的实现和回归测试，不应在追新功能时推倒重来。

但这仍是本机单用户执行环境。权限确认不是操作系统沙箱，检查点也不是跨文件、Shell、外部服务的事务。当前 Web 一次只允许一个前台任务，并固定启动目录。把它直接扩成云端多用户服务，会引入一整套新的问题。

## 3. 代码中最影响迭代方向的七个发现

### 3.1 技能评测与真实运行之间存在明显距离

[技能评测](D:/mawoagent/mawoagent/agents/online_skill_eval.py:366)直接把技能正文作为模型指令，重新生成文本答案，再执行格式检查和语义判分。样本审核还明确要求 `text_only=True`。

这可以检查文字输出回归，但没有通过完整 Agent Loop 验证：

- 检索能否找到正确技能，模型是否决定加载它。
- 加载后是否正确调用工具，是否完成真实文件或代码修改。
- 相似但不适用的任务是否受到污染。
- 成功是否来自更多推理预算、更强模型或额外提示，而非技能本身。

因此要同时保留两种测试：强制加载测试用于诊断技能内容；自然发现与执行测试用于判断用户实际能得到多少收益。不能用前者替代后者。

### 3.2 已有分组回归设计，下一步应增加真正独立的证据

当前实现已经重做当前版、候选版和冠军版，并按会话分组，避免重叠窗口跨开发/测试集合；还区分原任务重做与反馈修订。这些设计应保留。

但来源本身可能参与过技能学习，默认最小样本数为 2、晋级测试数为 1，且同一晋级集合可能被多轮比较使用。这适合早期回归门槛，不适合估计稳定泛化收益。需要额外的时间切分或未参与学习的任务集，并对反复使用的晋级集进行轮换。

依据见 [样本审核与分组](D:/mawoagent/mawoagent/agents/online_skill_eval.py:144)、[晋级比较](D:/mawoagent/mawoagent/agents/online_skill_eval.py:475)。

### 3.3 新技能冷启动没有自动评测闭环

正式评测路径要求技能已经存在于活跃快照中，待评候选主要取已有技能的 `merge`。新建 `add` 候选缺少活跃基线和使用统计，通常走人工审核发布。

这不是隐蔽行为，文档已经说明。但如果主卖点是学习新能力，必须提供“无此技能 / 新候选技能”的对照，冷启动可以在沙箱评测，不必先进入正式活跃库。见 [候选选择](D:/mawoagent/mawoagent/agents/online_skill_eval.py:605)、[发布保护](D:/mawoagent/mawoagent/agents/skill_candidates.py:120)。

### 3.4 检索与使用统计还不能说明贡献

现有检索是带中英文词项处理和元信息加权的 BM25 风格检索；默认取前三条。它并不是向量语义检索。候选管理还会向模型提供最多 80 条已有技能的内容片段。

目前活跃技能较少，优先级应是建立触发正例、反例和跨语言样本，修复描述解析，测量误召回与漏召回；然后再比较 BM25、向量检索和混合检索。不要先引入向量数据库再寻找问题。

“被检索”“模型认为被使用”“确实调用 skill 工具”“任务结果因此更好”是四件不同的事。当前使用统计更接近前两者，不能当作因果收益。见 [技能检索](D:/mawoagent/mawoagent/agents/skills.py:267)、[使用判定](D:/mawoagent/mawoagent/agents/online_skill_evolution.py:322)。

### 3.5 技能互操作存在一个现成的具体问题

[frontmatter 解析器](D:/mawoagent/mawoagent/agents/frontmatter.py:13)只处理简单的逐行 `key: value`。仓库内已有技能使用 YAML 多行 `description: |`；按当前解析器，该描述会变成字符串 `|`，影响展示与检索。嵌套 metadata、标准字段语义和目录命名也需要兼容性验证。

这比泛泛地增加一个“导入技能”按钮更重要。建议先实现完整、安全的 YAML frontmatter 读取与校验，区分内部扩展字段和标准字段，再做导入/导出往返测试。[Agent Skills 官方规范](https://agentskills.io/specification)定义了元信息、目录以及 scripts/references/assets 的结构与渐进加载方式。

当前版本和候选保护主要围绕 `SKILL.md` 正文。未来若演化 scripts 或 references，仅绑定正文不足以描述完整行为；应对整个技能包做清单、内容摘要与版本绑定。

### 3.6 项目定位尚未统一

README 定位为通用 Agent Runtime，系统提示默认定位编码助手，Web 欢迎页也是代码任务，而内置示例目前是代码审查与政府报告。

这体现可扩展性，却没有告诉新用户“为什么需要长期使用 mawoagent”。建议选择一个默认场景，其他示例移到明确的扩展目录。学习规则、长期事实和临时任务状态也要有清晰边界：

- 项目事实、当前决定与资源位置进入 Memory。
- 可重复执行的方法、检查步骤、稳定约束进入 Skill。
- 当前任务进度留在 Session。
- 展示风格和用户偏好可以有单独的轻量配置，避免每条偏好都膨胀成完整 Skill。

### 3.7 自动学习的默认权限体验需要更清楚

自动演化默认开启，但后台保存候选采用非交互授权；默认权限下，创建/演化技能需要确认，因此后台候选可能无法保存。如果已经完成抽取和维护判断，再遇到写入拒绝，还会产生没有形成候选的辅助模型开销。

建议明确区分“允许生成并保存学习草案”和“允许发布活跃技能”，在工作台显示学习状态与阻断原因，并在发出不必要的模型请求前检查可执行范围。这里的目标是把现有权限语义做成用户能理解的体验，而不是默默放宽发布权限。依据见 [后台授权](D:/mawoagent/mawoagent/agents/agent.py:714)及 [抽取后的维护与保存](D:/mawoagent/mawoagent/agents/online_skill_evolution.py:233)。

## 4. GitHub 项目对比：哪些已经是基础能力

Star 为 2026-10-18 访问官方仓库时页面显示的近似值，仅用于说明关注度，不是质量、用户数或增长排名。小型研究项目单列为直接机制对照。

| 项目 | 页面关注度 | 官方公开重点 | 对 mawoagent 的启示 |
| --- | ---: | --- | --- |
| [OpenClaw](https://github.com/openclaw/openclaw) | 约 392k | 跨平台个人助理与开放扩展生态 | 通用助理和广泛渠道接入竞争强；“本地运行、能用工具”不足以区分项目 |
| [Hermes Agent](https://github.com/NousResearch/hermes-agent) | 约 255k | 从经验创建/改进技能、跨会话记忆、消息网关、调度和多执行后端 | 与“会成长的个人 Agent”定位直接重叠；不能把技能学习本身当作独有卖点 |
| [OpenCode](https://github.com/anomalyco/opencode) | 约 216k | 开源编码 Agent、终端与桌面入口、模型选择 | 借鉴安装和日常交互；不应靠补齐整套编码工具功能清单建立优势 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | 约 91.2k | 当前官方仓库以 Agent Canvas 为中心，连接多种 Agent 和执行后端，并支持自动化 | 生态方向已经包括跨 Agent 控制面；自建完整平台代价很大 |
| [Deep Agents](https://github.com/langchain-ai/deepagents) | 约 30.4k | 文件系统、子 Agent、上下文、Skills、持久化、工具扩展与可替换后端 | mawoagent 的基础 Harness 功能与它高度重叠；轻量和可理解是优势，仍需用户效果来支撑定位 |
| [AutoSkill](https://github.com/ECNU-ICALK/AutoSkill) | 603 | 从交互经验抽取技能、合并、版本维护、检索；另有 SDK、代理与 SkillEvo | 是最接近的机制对照。抽取加版本化并不是新的差异；应比较端到端收益与审核体验 |
| [EvoSkill](https://github.com/sentient-agi/EvoSkill) | 约 1.3k | 从失败轨迹生成技能/提示变体，以独立验证集选择，适配多种执行器 | 跨 Agent 演化层已经有人做；可借鉴执行器适配与失败轨迹，但应找到自己的低摩擦使用场景 |

这里必须区分两个名字：LangChain 的 **Deep Agents** 是通用 Harness 项目；仓库论文对应的 **RUC DeepAgent** 是带自主工具发现、结构化记忆折叠和 ToolPO 训练方法的研究系统。mawoagent 实现了相近的折叠结构及对照评测入口，不能由此推导它复现了 ToolPO 或论文的成绩。研究系统说明见 [RUC DeepAgent](https://github.com/RUC-NLPIR/DeepAgent)。

“可验证”本身也不是独有机制，EvoSkill 已经强调验证与选择。潜在竞争力必须来自一个特定用户场景中更低的审核负担、更可靠的自然触发、可复现的执行收益，以及持续积累的“任务—纠正—规则—验收”数据。仅给现有机制换一个名字不构成差异。

## 5. 近期概念中，真正应该吸收什么

### 5.1 Harness 工程：把执行环境、会话与策略分开

Harness 的价值在于让任务完成得稳定，而不是把更多控制逻辑塞进提示词。Anthropic 2026-04-08 的工程文章把 Session、Harness 和 Sandbox 作为可替换的接口边界。[原文](https://www.anthropic.com/engineering/managed-agents)

对本项目的建议是：先把工作区、权限上下文、工具注册和事件记录变成实例级对象，让运行结果可回放、可测量。当前全局缓存与 `Path.cwd()` 耦合较多，直接增加并行会话或多工作区会放大状态串扰。无需为此马上拆成微服务或整体迁移框架。

### 5.2 ACE / GEPA：从失败中提炼局部改进

[ACE](https://github.com/ace-agent/ace)把上下文视作可积累、反思和维护的操作手册；[GEPA](https://github.com/gepa-ai/gepa)利用执行轨迹中的具体反馈提出变体并进行选择。

值得借鉴的是“哪一步失败、哪条规则缺失、如何用最小修改修复”，而不是每次重写整份技能。项目已有候选、完整正文、版本快照与基础摘要；可以进一步记录规则级增删、矛盾关系和变更理由。算法名或角色数量本身不会带来用户收益。

### 5.3 多轮自进化：多改几轮不等于持续进步

2026 年的 [Rethinking Self-Evolving Agent Skills](https://arxiv.org/abs/2608.02636)报告，在其控制实验中，388 个候选只有 55 个成为内容不同的验证最佳版本，效果依赖模型、任务和反馈类型。它支持“稀疏、经过验证筛选的搜索”这一判断，不能推广为所有 Agent 的固定收益规律。

对应决策：更重视候选拒绝、失败归因、停止条件和收益/成本曲线；允许系统明确说“没有足够证据更新技能”。技能文件数量和演化次数不应成为主指标。

### 5.4 真实技能调用：评测必须包含“会不会用”

2026-10-04 的预印本 [Agent Skill Evolution: How Revisions Affect Coding Agents](https://arxiv.org/abs/2610.04832)比较了强制给定技能与真实按需加载的情形，在它的实验中，按需加载后只能保留部分行动收益。

这直接对应本项目的评测缺口。需要把“内容质量”“选择/激活质量”“执行质量”分开记录，最终以自然调用路径的任务结果作产品验收。

### 5.5 可执行技能包：从 Markdown 演化走向脚本与产物验证

2026-10-02 提交、10-09 更新的预印本 [SkillScriptBench](https://arxiv.org/abs/2610.04008)区分文档修复、脚本修复和原有行为保持。它提醒我们：修改文档不代表修好了执行行为，允许修改更多文件也不代表更安全或更有效。

建议先为少量技能增加确定性的输入、脚本、验收与产物检查，再开放包级演化。发布对象需要同时绑定文档、脚本、依赖和测试结果；不必第一版就实现自动 AST 修改。

### 5.6 开放标准：先让技能可携带，再考虑连接更多界面

[Agent Skills](https://agentskills.io/specification)解决技能内容与资源的组织；[ACP](https://github.com/agentclientprotocol/agent-client-protocol)解决编辑器/客户端与编码 Agent 的通信。MCP 则用于工具与上下文扩展。三者角色不同。

本项目已经有 MCP 客户端，但没有因此自动拥有跨 Agent 学习接口。建议先完成标准技能导出和一个外部执行器适配，再根据实际接入需求选择 SDK、MCP 服务或 ACP。不要同时建设三个接口。

## 6. 头脑风暴后，我会如何取舍

以下是相对优先级判断，不是测量得出的市场评分。

| 方向 | 与现有资产契合度 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 可验证的技能学习工作台 | 高 | 还缺真实执行评测和用户收益证据 | 主线 |
| 重复工程任务的项目规范学习 | 高 | 必须证明能减少相同错误和纠正次数 | 首个场景假设 |
| 中文报告/内容生产的个性化工作流 | 较高 | 事实正确性、材料来源与交付格式需要另建能力 | 有真实种子用户时可作为替代首场景 |
| 跨 Agent 的学习 SDK/服务 | 中高 | 外部执行器、权限语义和技能兼容成本 | 效果证明后的扩展方式 |
| 通用编码 IDE/桌面工具 | 中 | 功能面和成熟生态竞争 | 只补必要使用体验 |
| 多渠道、常驻个人助理 | 中低 | 网关、调度、远程运行与安全投入大 | 暂缓 |
| 多 Agent 群体协作平台 | 低 | 当前执行主要是 fork-return，且 Web 单前台任务 | 暂缓，先验证单执行器闭环 |
| 自动修改自身 Runtime / 强化学习训练 | 低 | 测量、隔离、算力和回归成本远超当前基础 | 研究支线，不进入近期产品主线 |
| 技能市场、图谱记忆、大规模向量基础设施 | 低至中 | 尚无规模与需求证据 | 不预建 |

**选择首场景时，我暂时偏向“同一代码仓库中的重复维护任务”。** 原因不是开发者市场一定更好，而是当前工具、提示词、UI 和测试基础更匹配，而且命令、测试与文件差异提供较强验收信号。

例如：用户反复纠正测试命令、修改目录、接口兼容要求、报告交付格式。系统应把这些纠正提炼成适用范围明确的工作步骤，在另一项同类任务中执行并验证。第一版可只选择一种：例如测试驱动的小修复或固定格式的代码审查。

如果实际用户主要做报告或写作，应切换首场景，但继续使用同一个学习与评测内核。不能仅凭仓库放了哪些 Skill，推断已经存在对应需求。

## 7. 第一轮迭代：先把效果证据和审核体验做完整

不按日历估算，按验收门槛推进。

### P0-A：记录一条可追溯的完整任务轨迹

在现有检查点上补充统一的事件记录，至少关联：run/session、原始输入、模型与配置、技能版本/包摘要、检索候选、实际激活、工具调用与结果、产物摘要、验收结果、主/辅助调用用量、用户纠正。

不要简单把所有工具输出永久塞进一份 JSON：保留现有大结果引用机制。不要把模型自报“已完成”作为任务成功。副作用工具必须在隔离工作区运行，对外部系统调用使用测试环境或录制替身。

验收：任一学习候选都能点回证据；任一评测结论都能重建使用的技能包、运行条件和任务结果。

### P0-B：把技能评测升级为可执行的实验

新增至少两类执行器：保留现有文本执行器；增加当前 Agent Runtime 的沙箱执行器。

比较最少四种条件：无新增技能、旧版技能、新候选技能、等预算的普通提示或重试。不要把更换模型、更换工具、增加调用预算与技能更新混在同一个实验里。

强制加载用于定位内容缺陷；自然选择用于确认实际收益。新技能以“无该技能”为基线，既有技能以旧版为基线。使用固定且记录完整的条件，按任务配对比较，记录失败与不完整尝试，不能只统计成功结束的样本。

验收：评测中真正完成文件或代码任务，使用程序检查产物；候选必须既改善目标任务，又通过相似任务和不应触发任务的保护检查。

### P0-C：把手改 JSONL 变成审核流程

现有 Web 能展示候选和评测报告，但样本审核仍主要依赖磁盘中的 review 文件，候选也缺少清晰的旧版/新版差异呈现。

优先增加三个界面能力：

1. 来源对话与目标轮次选择，并明确“重做原任务 / 修订已有答案”。
2. 自动生成验收草案，用户修改确认；生成者不能自行批准自己的验收条件。
3. 旧版/候选差异、测试通过/失败项、模型与成本、发布原因与回退入口。

候选正文、review、基础版本与评测运行必须保持现有摘要绑定。内容改动后旧评测失效。未知、数据不足、人工发布、评测通过应分别展示。

### P0-D：修好技能格式与触发测试

支持 YAML 多行描述；增加标准技能导入校验；为现有技能建立正例与反例；区分“检索到了”“加载了”“执行成功了”。先测试词项检索，再决定是否添加 embedding。本轮已用仓库中的真实多行描述技能运行现有解析器，返回值确实为字符串 `|`。

验收：仓库内真实技能描述可正确读出；导入/导出不丢元信息与引用；相似任务的误触发可测量。

## 8. 第二、三轮：在证据成立后扩大能力

### P1：做一个能被用户感知的重复任务闭环

选择一类真实任务，招募少量愿意重复使用的用户。5–10 名可作为第一轮访谈与体验样本的建议规模，不代表市场验证完成。

每名用户比较学习前后若干同类但不同输入的任务，重点追踪：相同错误是否复发、纠正次数是否降低、交付物是否更快达到验收。给出可重复运行的公开演示和评测样本，而不只展示模型说“我记住了”。

同时做新技能冷启动评测、范围/冲突管理、小规模技能包支持。个人偏好与项目规则发生冲突时，要能说明采用哪一条和原因。

### P2：开放一个外部执行器

把学习模块从主 Agent 类的状态依赖中提取出清晰接口，概念上分别接收 Experience、Candidate、Evaluation 和 Publication 决定。先保持同一进程、同一部署，不以架构拆分本身作为成果。

提供标准技能包导出，并适配一个外部执行器。只有在新任务上有可复现收益时，才宣传技能可迁移。更换模型或执行器后应重新验证，不能直接继承旧执行器的通过状态。

最后再考虑多工作区、任务并发、远程执行和更多界面。现有 Runtime 的轻量、易读和低依赖值得保留。

## 9. 具体实验与指标

建议先构建一个小而清晰的任务集，例如 30–50 个任务，分成可自动验收的维护任务、相似任务和负例；这只是先导实验规模，不能自动保证统计显著。按仓库、会话来源和任务模板分组，另留时间更晚、未参与学习的任务。

对关键条件做多次重复，报告配对胜负、成功率差异和不确定性范围。采用多少次重复、多少样本，应由先导实验的波动与希望检测的差异决定。固定开发/验证/最终测试的用途，最终测试不参与选候选；反复选择所用的验证集需要监测过拟合。

| 指标 | 解决的问题 |
| --- | --- |
| 任务验收成功率、首次通过率 | 是否真正完成工作 |
| 每个完成任务所需的用户纠正次数 | 用户是否少返工 |
| 同类错误复发率 | 纠正是否变成稳定经验 |
| 自然触发的精确率、召回率 | 该用时会不会用、不该用时是否乱用 |
| 目标任务收益与保护集退化 | 是否改善一处却损坏其他行为 |
| 主模型、辅助调用、评测的完整用量与耗时 | 学习带来的收益是否抵得上成本 |
| 审核耗时、候选采纳率与回退率 | 审核负担是否可接受 |
| 不同模型/执行器上的迁移表现 | 可携带性是否得到证实 |

主产品指标应围绕“经真实验收、减少重复纠正的任务”，不能用技能数量、更新次数、检索次数代替。

学习成本还应考虑未来复用次数。一个建议的核算方式是：在预计复用次数内，节省的执行成本和返工时间价值是否覆盖抽取、评测和审核成本。时间价值需要用户数据，不应在报告里任意折算为金额。

## 11. 如果目标是研究论文，什么问题更值得做

目前把基础 Runtime、AutoSkill 风格抽取与 DeepAgent 风格折叠整合起来，更像工程集成贡献。要形成研究贡献，应该选一个清晰、可证伪的问题：

- **反馈归因**：如何区分稳定偏好、任务内修订与真正可复用的方法？能否减少错误学习与人工审核？
- **技能选择与内容联合优化**：只改正文与同时优化触发条件相比，自然调用的收益差多少？
- **状态到方法的抽象**：会话中的工具经验，何时能够成为跨任务 Skill，如何防止把偶然路径和错误事实固化？
- **预算约束下的演化**：何时值得学习、何时应停止、收益何时覆盖学习成本？
- **包级安全演化**：如何同时修正文档与脚本，并证明既有行为得到保持？

其中“自然触发下的反馈归因与技能收益”最贴近当前基础。需要与直接记忆、普通提示追加、AutoSkill/EvoSkill 风格方案等做等预算对比，不能只与无记忆的空白 Agent 比较。
