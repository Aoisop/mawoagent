# mawoagent 技术亮点

## 1. 项目定位

mawoagent 的核心是 Harness，不是聊天壳。

模型负责推理和提出工具调用意图，Runtime 负责真正执行环境动作，并维持整个闭环：

```text
用户输入
  -> 构建 system prompt / Skills / Memory / 工具上下文
  -> 调用 OpenAI / Anthropic 兼容模型
  -> 解析文本或 tool call
  -> 权限检查
  -> 执行内置工具 / Skills / MCP / 子 Agent
  -> 工具结果回写模型
  -> 必要时压缩上下文
  -> 保存 session
  -> 触发 Skills 自进化和使用统计
```

这意味着 mawoagent 的技术重点不是单点能力，而是整个运行时的组织方式。

## 2. 技术亮点总览

| 亮点 | 价值 | 主要代码 |
|------|------|----------|

## 3. Agentic Harness

### 解决的问题

普通聊天应用只做“输入 -> 回复”。
Agent 需要多出一层：推理、执行、观察、继续推理。

mawoagent 把这层抽象成一个清楚的 Runtime，而不是散落在提示词里。

### 实现方式

核心入口是 `Agent.chat()`：

```text
初始化 MCP
  -> 检索并注入 Skills
  -> 预取 Memory
  -> 进入 OpenAI 或 Anthropic 主循环
  -> 模型返回文本或 tool call
  -> Runtime 统一做权限检查
  -> 执行工具 / Skill / MCP / 子 Agent
  -> 回写 tool result
  -> 后台触发 Skills usage tracking 和 online evolution
  -> 保存 session
```

工具分发统一收敛到 `_execute_tool_call()`，避免逻辑分叉。

### 价值

- 模型和环境动作分离。
- 所有能力纳入同一条 agent loop。
- 支持后续扩展工具、技能和外部服务。
- 便于调试、回放和审计。

## 4. 双协议模型接入

### 解决的问题

不同模型服务的协议不一样。
如果 Runtime 只能绑定一种 API，扩展和替换成本就会很高。

### 实现方式

`agents/main.py` 会根据 `.env`、`--api-base` 和环境变量判断协议：

- OpenAI-compatible
- Anthropic-compatible

`agents/agent.py` 里分别实现 `_chat_openai()` 和 `_chat_anthropic()`，但二者共享：

- 同一套工具定义
- 同一套权限系统
- 同一套 Memory / Skills 机制
- 同一套 session 和自进化流程

### 价值

- 同一份 Runtime 可以接不同模型服务。
- 迁移模型时不用重写工具系统。
- 方便对比不同协议下的行为差异。

## 5. 工具系统与权限控制

### 解决的问题

Agent 一旦能读写文件、执行 Shell、调用外部工具，就必须有控制边界。

### 实现方式

`agents/tools.py` 定义了核心工具：

- `read_file`
- `write_file`
- `edit_file`
- `list_files`
- `grep_search`
- `run_shell`
- `skill`
- `compact_context`
- `skill_create`
- `skill_evolve`
- `agent`
- `tool_search`

权限分层也在这里：

- `read_file`、`list_files`、`grep_search`、`compact_context` 默认允许。
- `plan` 模式下阻断普通写操作和 `run_shell`。
- `acceptEdits` 允许编辑类操作。
- `bypassPermissions` 直接放行。
- `dontAsk` 自动拒绝需要确认的动作。

还包含这些保护：

- 默认模式下每次 Shell 调用都需确认，避免解释器或管道写盘绕过命令黑名单。
- 默认模式下 `write_file`、`edit_file` 每次都需确认；`acceptEdits` 可自动批准这两个专用文件工具。
- 编辑前必须先读文件。
- 文件被外部修改后需要重新读取。

### 价值

- 模型只能提议动作，不能绕过 Runtime。
- 减少误改文件和危险命令风险。
- 让工具系统可控、可解释、可扩展。

## 6. Plan Mode

### 解决的问题

复杂修改如果直接进入执行态，很容易乱改。

### 实现方式

Plan Mode 在 `agents/agent.py` 和 `agents/tools.py` 里配合实现：

- 只读分析。
- 允许写计划文件。
- 阻断普通写操作和 Shell。
- 通过 `enter_plan_mode` / `exit_plan_mode` 完成切换。

### 价值

- 先规划，再执行。
- 降低大范围修改风险。
- 适合重构、排查和多文件任务。

## 7. Memory + Skills 分层长期上下文

### 解决的问题

Agent 需要同时记住两类信息：

- 事实和偏好。
- 方法和流程。

如果混在一起，上下文会变脏。

### 实现方式

`agents/memory.py` 负责 Memory：

- 项目路径 hash 隔离。
- 文件型 Markdown 记忆。
- 侧重事实、偏好、项目背景、历史决策。

`agents/skills.py` 负责 Skills：

- 目录型 `SKILL.md`。
- 用户级和项目级加载。
- BM25-lite 检索。
- inline / fork 执行。

### 价值

- Memory 记“这是什么”。
- Skills 记“这类事以后怎么做”。
- 分层后长期上下文更可控。

## 8. Skills 自进化

### 解决的问题

用户反复强调的稳定规则，不应该只留在当前会话里。

### 实现方式

自进化链路是：

```text
当前任务和回答
  -> 保存 pending window
下一轮用户反馈
  -> Extractor 抽取候选 Skill
  -> Maintainer 判断 add / merge / discard
  -> create_skill_file() 或 evolve_skill_file()
  -> 记录 provenance、history 和 usage stats
```

Extractor 只负责抽取候选，不写文件。

Maintainer 负责和已有 Skills 做相似度比较，并决定是否新增、合并或丢弃。

写入最终收敛到 `agents/skill_evolution.py`，统一版本、快照和审计。

### 价值

- 把用户反馈变成可复用方法。
- 避免 Skill 越积越多、越积越重复。
- 让沉淀过程可追踪、可回放、可治理。

## 9. Skills 质量评测

### 解决的问题

技能沉淀之后，不能默认它就有用。

### 实现方式

`agents/online_skill_eval.py` 提供评测链路，围绕：

- provenance
- usage stats
- replay 样本
- 规则评测
- LLM judge
- 候选版本试跑

项目 wiki 记录了 GAIA / HLE 的数据集与拟采用的评测口径，并明确区分 DeepAgent 论文结果和 mawoagent 尚未完成的实测；见[评测部分](折叠评测部分.md)。

### 价值

- 让 Skill 不是“写进去就算了”。
- 能观察是否真的被使用。
- 可以形成本地健康版本和候选版本对比。

## 10. 长程会话压缩

### 解决的问题

长任务会产生大量工具结果和中间状态，单纯保留原始历史会很快膨胀。

### 实现方式

`agents/agent.py` 负责自动压缩和主动压缩：

- `compact_context` 工具。
- 上下文阈值判断。
- 工具结果截断和持久化。
- session memory folding。

`agents/session.py` 负责把会话和折叠状态保存下来。

### 价值

- 让长对话可继续推进。
- 保留任务进度、阻塞点和工具经验。
- 不依赖完整原始历史也能恢复任务。

## 11. MCP 外部工具接入

### 解决的问题

外部能力不应该被硬编码进 Runtime。

### 实现方式

`agents/mcp_client.py` 自己实现 stdio JSON-RPC MCP Client：

```text
读取配置
  -> 启动 MCP server
  -> initialize
  -> tools/list
  -> 包装成 mcp__server__tool
  -> 调用时路由到 tools/call
```

配置来源包括：

- `~/.mawoagent/settings.json`
- `<project>/.mawoagent/settings.json`
- `<project>/.mcp.json`

### 价值

- 外部系统可以统一接入同一套工具层。
- 不污染主 Runtime 的职责。
- 适合浏览器、搜索、数据库和内部系统扩展。

## 12. 子 Agent

### 解决的问题

有些任务不适合在主上下文里直接做。

### 实现方式

`agents/subagent.py` 提供：

- `explore`
- `plan`
- `general`
- 自定义子 Agent

子 Agent 有独立上下文，能用更窄的工具集处理局部任务。

### 价值

- 降低主上下文噪声。
- 让探索、规划和局部分析分工更清晰。
- 方便定义专门角色。

## 13. 可观测性和审计

### 解决的问题

一个 Agent Runtime 如果不能回看，就很难持续迭代。

### 实现方式

项目把主要行为都落到本地文件里：

- `usage.jsonl`
- `online_provenance.jsonl`
- `online_skill_provenance.json`
- `skill_usage_stats.json`
- `history/`
- `pruned/`

这些记录可以追踪：

- 某个 Skill 为什么被创建。
- 某次沉淀为什么被 merge 或 discard。
- 某个 Skill 有没有真的被用上。
- 哪些能力已经变 stale。

### 价值

- 自进化过程可审计。
- 方便定位问题和回滚。
- 便于展示项目的工程完整性。

## 14. 简历级提炼

如果要压缩成几条技术亮点，可以这么写：

- 自研 Agentic Harness，统一编排模型推理、tool call 解析、权限检查、工具执行、结果回写、会话保存和上下文压缩。
- 实现双协议模型接入，兼容 OpenAI-compatible 和 Anthropic-compatible 接口，保持同一套工具、Memory 和 Skills Runtime。
- 设计工具与权限边界，支持 Plan Mode、危险命令检查、编辑前读取和文件 mtime 校验，降低误操作风险。
- 构建 Memory + Skills 分层长期上下文，Memory 保存事实和偏好，Skills 保存可复用方法和工作流。
- 实现 Skills 自进化闭环，通过 pending window、Extractor、Maintainer、provenance 和 usage stats，把用户反馈沉淀成可治理的 `SKILL.md`。
- 接入 MCP 和子 Agent 机制，把外部工具和隔离任务统一纳入同一运行时。
- 提供长程任务压缩和 session folding，让 Agent 在上下文膨胀后仍能继续推进任务。
