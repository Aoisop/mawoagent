# 为什么还要做 mawoagent

今天已经有很多非常强的 Agent 产品和框架。模型能力越来越强，工具调用也越来越成熟，看起来似乎已经没有必要再从头写一个 Agent。

但 mawoagent 想回答的问题不是“能不能再做一个聊天工具”，也不是“能不能再做一个 Coding Agent”。它真正想回答的是：

**如果我们想理解、控制并持续演化一个通用 Agent，它的底层运行时应该长什么样？**

mawoagent 的定位是一个通用类型的 Agent。它参考了 Claude Code（cc）这类产品在底层架构上的设计思想，比如 agent loop、工具调用、权限边界、上下文管理、子 Agent、Skills 和任务状态恢复。但 mawoagent 不是 Coding Agent，它的目标不是围绕软件工程场景做垂直优化，而是做一个更通用、更容易学习、更容易二次开发的 Agent Runtime。

所以在 mawoagent 里，你不会看到围绕工程流程堆出来的一整套垂直工具链。它的核心是：让模型能够在一个清楚、可控、可扩展的运行时里完成通用任务，并且在使用过程中通过 Skills 自进化沉淀长期能力。

## 1. 为什么不是再做一个 Coding Agent

Coding Agent 已经有很强的成熟产品。它们擅长处理软件工程里的复杂任务，也已经形成了非常完整的产品体验。

mawoagent 不想在这个方向上重复造一个同类产品。它更关注的是 Agent 背后的通用机制：

- 模型如何在多轮任务中持续推进；
- 工具如何被统一描述、调用和管理；
- 上下文变长后如何保留关键状态；
- 用户反馈如何沉淀成可复用能力；
- Agent 如何在长程任务里恢复、继续和纠偏；
- 新能力如何被记录、审计和评测；
- 一个复杂 Agent 系统如何保持代码足够清楚，方便学习和改造。

这些问题并不只属于 Coding Agent。写作、研究、信息整理、文档生成、学习辅导、流程执行、资料分析、个人助理、垂直领域任务，都需要类似的底层能力。

因此，mawoagent 的核心不是“写代码”，而是“通用 Agent Runtime”。

## 2. 参考 cc，但不复制 cc 的产品定位

Claude Code 这类产品很值得学习，因为它们证明了一件事：Agent 的能力不只来自模型本身，还来自模型外面那层工程系统。

这层系统至少包括：

- agent loop；
- system prompt 构建；
- tool call 解析；
- 工具执行和结果回写；
- 权限控制；
- 上下文压缩；
- session 保存和恢复；
- 子 Agent；
- Skills；
- 长程任务状态管理。

mawoagent 参考的是这些底层架构思想，而不是照搬 Coding Agent 的产品边界。

换句话说，cc 给 mawoagent 的启发是：一个真正可用的 Agent 必须有 Harness，不能只是“用户输入 -> 调模型 -> 输出结果”。但 mawoagent 要把这套 Harness 做成通用底座，让它可以服务更广泛的任务，而不是只服务代码场景。

## 3. mawoagent 的核心是一个清楚的 Agent Loop

普通模型应用通常是：

```text
用户输入 -> 调用模型 -> 返回回复
```

mawoagent 的运行链路更接近：

```text
用户输入
  -> 构建 system prompt、Memory、Skills 和工具上下文
  -> 调用 OpenAI / Anthropic 兼容模型
  -> 解析模型返回的文本或 tool call
  -> 由 Runtime 判断是否允许执行
  -> 执行内置工具、MCP 工具、Skills 或子 Agent
  -> 将工具结果回写给模型
  -> 必要时压缩和重组上下文
  -> 保存 session
  -> 根据用户反馈触发 Skills 自进化和评测
```

这里最重要的区别是：模型负责推理和提出意图，Runtime 负责真正的执行边界。

mawoagent 不是把模型直接暴露给环境，而是用一个统一的 Agent Loop 把模型、工具、记忆、Skills、子 Agent、上下文和会话状态组织起来。这样做的好处是可控、可观察，也方便继续演化。

## 4. 为什么通用 Agent 更需要 Skills 自进化

通用 Agent 面对的任务非常分散。今天可能是写一份材料，明天可能是分析一篇文章，后天可能是整理一个复杂项目，再之后可能是生成一个特定风格的输出。

如果每次都只靠当前上下文，用户就必须反复说明自己的偏好和方法。例如：

- “以后写总结先给结论，再展开理由。”
- “这类文档不要写成营销风，要更克制、更像内部材料。”
- “整理资料时先分层归纳，再列可执行事项。”
- “不要把一次性事实沉淀下来，只沉淀可复用的方法。”
- “遇到长任务时先建立任务状态，再逐步推进。”

这些反馈不是某一次任务的临时要求，而是未来可以复用的工作方式。

mawoagent 的 Skills 自进化就是为了解决这个问题。它会从用户反馈中抽取稳定规则，沉淀成 `SKILL.md`，让 Agent 在后续相似任务中自动调用这些能力。

它沉淀的不是某次对话内容，而是可复用能力：

- 输出规范；
- 工作流；
- 判断标准；
- 任务触发条件；
- 用户偏好；
- 领域方法；
- 可复用的执行步骤。

这也是 mawoagent 和普通聊天工具最大的区别之一：普通聊天工具更多是在当前会话里变聪明，mawoagent 希望把稳定反馈变成长期能力。

## 5. 自进化不是让模型随便改自己

Skills 自进化听起来很激进，但 mawoagent 的设计是保守的。

它不是让模型在每轮对话后自我总结“我学到了什么”，然后随便修改自己的提示词。mawoagent 更强调证据链和可审计：

```text
本轮用户请求 + assistant 回复
  -> 保存 pending window
下一轮用户反馈
  -> 合并为证据
  -> 抽取最多一个候选 Skill
  -> 检索相似 Skills
  -> 决策 add / merge / discard
  -> 写入或演化 SKILL.md
  -> 记录来源、版本快照和使用统计
```

这里的关键是：用用户后续反馈作为证据，而不是让模型凭空判断自己应该学什么。

这样可以减少几类风险：

- 把一次性任务事实误沉淀成长期规则；
- 把隐私、账号、链接、精确日期写进长期能力；
- 把模型自己的幻觉当成经验；
- Skill 越积越多但质量不可控；
- 新旧规则冲突后无法追踪来源。

mawoagent 希望自进化是可追踪、可回放、可评测的，而不是一个黑盒的“自动变聪明”。

## 6. 为什么要支持长程任务

Agent 真正困难的地方，往往不是回答一个问题，而是连续推进一个任务。

长程任务里会出现很多问题：

- 上下文越来越长；
- 中间结论越来越多；
- 工具结果和失败路径越来越多；
- 当前目标容易被历史信息淹没；
- 用户中途补充要求后，任务状态需要重新整理；
- 会话中断后，Agent 需要知道自己做到哪里。

如果只做简单摘要，很多关键状态会丢失。如果只靠完整上下文，又会很快遇到长度和噪声问题。

mawoagent 因此把长程任务当成核心能力之一。它会把会话历史折叠成更适合继续执行的状态，例如：

```text
episode_memory
  -> 任务描述、关键事件、当前进度

working_memory
  -> 当前子目标、阻塞点、下一步动作

tool_memory
  -> 已使用工具、有效参数、常见错误、返回模式
```

这不是单纯为了省 token，而是为了让 Agent 在长任务里完成状态重组。

长程任务需要的不是“记住所有字”，而是“知道现在要继续做什么”。mawoagent 的上下文折叠、session 保存、Memory、Skills 和子 Agent 都是围绕这个目标设计的。

## 7. 为什么通用 Agent 也需要工具和权限边界

即使 mawoagent 不是 Coding Agent，它也仍然需要工具系统。

通用任务也会涉及很多外部动作：

- 读取本地资料；
- 搜索和整理信息；
- 调用外部 MCP 工具；
- 执行特定领域能力；
- 让子 Agent 完成局部分析；
- 把中间结果保存为可恢复的状态；
- 调用 Skills 完成特定工作流。

但工具一旦接入，就必须有边界。mawoagent 的设计原则是：模型提出意图，Runtime 管理执行。

这意味着工具调用不是模型随意行动，而是要经过统一的分发、权限判断、结果截断、错误处理和会话记录。这样才能让通用 Agent 在扩展能力的同时，仍然保持可控。

## 8. 一个更具体的包装场景：公司内部日志排查 Agent

因为 mawoagent 的定位是通用类型的 Agent，所以它完全可以和实习场景、横向业务场景或公司内部流程结合。

比如做一个公司内部的日志排查 Agent，可以这样包装：

```text
公司机器鉴权接口
  -> 包装成 auth tool

日志查询接口
  -> 包装成 log search tool

服务状态接口
  -> 包装成 service status tool

排查经验、常见坑、步骤规范
  -> 写成对应的 SKILL.md

排查完成后的结果反馈
  -> 通过 hook 或 feedback tool 回写到内部系统
```

一次实际任务可能是：

```text
用户输入：
帮我排查订单服务今天下午 3 点之后的报错原因。

mawoagent 执行：
  -> 根据任务识别需要日志排查能力
  -> 自动加载对应的日志排查 Skill
  -> 调用公司机器鉴权 tool
  -> 调用日志查询 tool 拉取相关时间段日志
  -> 调用服务状态 tool 检查实例、发布、依赖状态
  -> 按 Skill 里的排查步骤分析异常模式
  -> 总结根因、影响范围、证据和建议动作
  -> 最后通过 feedback tool 把排查结果回写到内部系统
```

这里 mawoagent 并不需要变成一个专门的日志平台。它只需要提供通用 Agent Runtime：

- 外部接口可以定义成 tool；
- 内部排查经验可以定义成 Skill；
- 固定收尾动作可以定义成 hook 或 tool；
- 多轮分析过程可以依靠长程任务状态继续推进；
- 用户后续反馈可以继续沉淀到 Skill 里。

这个例子说明 mawoagent 的通用性：它不是为某一个垂直任务写死逻辑，而是让不同场景都可以通过“工具 + Skills + Memory + hooks + agent loop”的方式接入。

## 9. 为什么要保持代码量克制

mawoagent 还有一个很重要的目标：适合学习。

很多 Agent 框架功能很全，但代码层级复杂，抽象很多，想看懂完整执行链路并不容易。mawoagent 从写第一行代码开始，就刻意控制代码量和抽象数量。

现在即使加上 Skills 自进化和长程任务能力，核心 Agent 代码也大约只有 9000 行 Python。它不是一个堆满平台化概念的大框架，而是一个围绕 agent loop 展开的轻量系统。

这种克制有几个好处：

- 读者可以从入口一路看到模型调用、工具调度、上下文处理和 session 保存；
- 代码风格直接，不需要先理解大量框架概念；
- 每个模块的职责比较清楚；
- 想替换模型、工具、记忆、Skills 或评测链路都比较容易；
- 适合学习 Agent 的底层原理，也适合继续实验。

轻量不是功能少，而是把核心路径保持清楚。mawoagent 的目标不是做一个复杂平台，而是做一个足够完整、足够可读、足够可改的 Agent Runtime。

## 10. mawoagent 真正想验证什么

mawoagent 想验证的不是“模型能不能完成某个单点任务”，而是更底层的几个问题：

- 一个通用 Agent 能不能用清楚的 agent loop 组织起来；
- 长程任务状态能不能被结构化保存和恢复；
- 用户反馈能不能自动沉淀成可复用 Skills；
- Skills 自进化能不能做到可审计、可评测、可回滚；
- MCP、子 Agent、Memory 和 Skills 能不能进入同一个运行时；
- 一个 Agent 项目能不能在功能增长后仍然保持足够容易学习。

这也是 mawoagent 值得做的原因。

它不是成熟 Agent 产品的替代品，也不是另一个 Coding Agent。它更像一个可以打开、阅读、修改和继续演化的通用 Agent 底座。

## 11. 一句话总结

mawoagent 之所以值得做，是因为我们需要一个**参考成熟 Agent 底层架构、但定位于通用任务，支持 Skills 自进化和长程任务，同时保持代码足够精简清楚的 Agent Runtime**。

它真正关注的是：

**如何把一次性对话变成可持续推进的任务状态，把用户反馈变成可复用能力，并用一个只有清晰 agent loop 的轻量工程系统，让通用 Agent 变得可学习、可控制、可演化。**
