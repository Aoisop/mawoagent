# 在线 Skills 评测实现说明：从 U1 A1 U2 A2 U3 理解整个流程


本文先讲思路，再讲操作与代码。贯穿全文的问题是：**经历了用户纠错之后，当前 Skill C 重新完成任务的表现如何？评测提出的候选 D 有没有更好？**

当前入口是 mawoagent REPL 中的 `/skill-eval`。它运行的是经人工确认的文本任务回归评测，调用辅助模型生成答案和评分，不执行完整 Agent 的工具操作。

## 一、先区分三个东西：对话证据、评测题目、Skill 版本

这三个概念混在一起，最容易导致“到底在评谁”的困惑。

| 概念 | 例子 | 作用 |
| --- | --- | --- |
| 对话证据 | `U1 A1 U2 A2 U3` | 说明用户问过什么、助手答过什么、用户如何反馈 |
| 评测题目 | “重答 U1，使用 U1 之前的上下文，按已确认条件验收” | 明确本轮模型到底要完成什么 |
| Skill 版本 | 当前 C、候选 D、已有冠军 | 在相同题目上分别使用的指令版本 |

**一段对话窗口不会直接变成一个问句。** 程序先保留证据，再通过审核把证据中的某个用户消息绑定成明确的评测目标。

文中的 `Skill A / B / C / D` 是同一个 Skill 的不同版本；`A1 / A2` 是历史助手回答，两者不要混淆。

## 二、用一段具体对话代替抽象符号

假设真实对话如下：

| 消息 | 内容 |
| --- | --- |
| U1 | “请只输出 JSON，包含 summary 和 risks，说明把配置直接覆盖写入文件的风险。” |
| A1 | 助手输出了一段普通文字，没有遵守 JSON 格式。 |
| U2 | “你没有按 JSON 格式回答，请按我刚才的要求重写。” |
| A2 | 助手输出了 JSON，但 risks 没有提到写入中断可能损坏文件。 |
| U3 | “还漏了写入中断损坏文件的风险，请补充。” |

原有 Skill A 可能从第一段反馈中演化成 B，随后进一步演化成 C。这里的 A→B→C 用来解释版本关系，**不表示每次反馈一定会创建版本**：实际在线演化可能新增、合并、丢弃候选，也可能失败或被拒绝。

还有一个时序细节：用户下一条消息到来时，程序取出上一轮 pending window；通常在当前回复完成后，才调度上一窗口的后台演化。因此不能仅凭对话顺序断言 A2 已经使用了 B。本文后面的评测会明确加载当时的活跃快照 C，重新生成答案。

## 三、Replay 从哪里来，原始信息怎样保存

### 3.1 来源确实包含 online_provenance.jsonl

评测器按 Skill 名称收集以下来源：

- `.mawoagent/skill-evolution/online_provenance.jsonl`：在线演化日志。
- `.mawoagent/skill-evolution/online_skill_provenance.json`：按 Skill 整理的来源索引。
- `online-eval/datasets/<lineage>/replay_pool_v2.jsonl`：已保存的来源样本池。
- 旧版 `replay_pool.jsonl`：兼容导入，只作为待审核证据，不继承旧分组或分数。

没有关联到某个 Skill 的日志事件，不会自动成为该 Skill 的评测题。日志同时出现在索引里时，会按来源身份去重。

### 3.2 新记录把“上一请求”和“下一条消息”分开保存

`Agent._set_pending_skill_extraction_window()` 保存 `replay_context`。对上面的例子，可以理解为：

| 来源窗口 | 捕获的 task_user | 请求前 context_messages | original_response | 后续 feedback |
| --- | --- | --- | --- | --- |
| `U1 A1 U2` | U1 | 空 | A1 | U2 |
| `U1 A1 U2 A2 U3` | U2 | U1、A1 | A2 | U3 |

注意：这里的 `task_user=U2` 只是记录“A2 当时是在回应 U2”，**尚未决定评测必须重答 U2**。最后到底重答谁，要看后续目标绑定。

记录还包含 session_id 和 event_id，分别用于会话归属和来源身份。旧的 `latest_user/latest_assistant` 不再充当最终评测目标的依据。

当前 Agent 单独保留最近 8 条原始用户/助手上下文，不包含检索注入的 Skill 文本和工具消息。早期任务不在窗口中、会话恢复后缺少必要上下文、任务需要工具或外部资料时，不能假定这条回放已经完整，应保持未批准。

### 3.3 旧日志只能提供建议，不能自动确定语义

没有 `replay_context` 的旧日志，程序尝试找到最后一个助手回答，以及它前面的用户请求，把它们整理成待审核证据。

对 `U1 A1 U2 A2 U3`，这个建议会落在 U2/A2。它只是在还原历史问答配对，无法自动判断 U2 是新任务还是纠错。

新记录、旧记录都需要审核。**“下一句用户消息”并不天然等于“可以信任的纠错标准”。**

## 四、这次最关键的修改：明确选择重答哪一轮

程序把来源重建为带位置的 `source_turns`。本例没有更早上下文，因此编号如下：

```text
index 0 → U1
index 1 → A1
index 2 → U2
index 3 → A2
index 4 → U3
```

这是每条来源记录内从 0 开始的位置，不是所有会话共用的编号。有更早上下文时，U1 不一定在 0，必须查看生成的 `source_turns`。

### 4.1 方式一：原任务重做 original_task

要回答的问题是：**现在使用 C，不看以前的答案，能不能把最初的 U1 做对？**

审核设置：

```json
{
  "evaluation_mode": "original_task",
  "target_turn_index": 0,
  "feedback_parent_turn_index": null
}
```

程序自动重建：

```text
题目：U1
上下文：source_turns[0:0]，本例为空
被排除：A1、U2、A2、U3
```

生成模型看到的是：

```text
当前 Skill C + U1
```

候选比较时看到的是：

```text
候选 Skill D + 同一个 U1
```

原始 A1 不参与本轮计分，也不会作为参考答案发给作答模型。

如果 U1 之前本来有必要对话，程序会保留那部分。所谓“重做”是从选定用户请求之前的状态重新回答，不是强制清空所有历史。

### 4.2 方式二：反馈修正 feedback_revision

要回答的问题变成：**已经有了 U1/A1，用户提出 U2 纠错后，当前版本能不能正确修改？**

审核设置：

```json
{
  "evaluation_mode": "feedback_revision",
  "target_turn_index": 2,
  "feedback_parent_turn_index": 0
}
```

程序自动重建：

```text
题目：U2
上下文：U1、A1
被排除：A2、U3
```

这里让模型回答 U2 是合适的，因为测的就是反馈修正能力。A1 属于必要历史，允许保留；A2 才是本题的历史目标回答，必须排除。

`feedback_parent_turn_index` 用于明确用户认为 U2 在纠正哪个更早请求，并验证该请求位置合法；上下文仍取目标位置之前的全部已保存消息，不是只截取 parent 附近的两个消息。

### 4.3 程序不允许只改 task_user，却忘记清理上下文

之前的漏洞是：把题目文字从 U2 改成 U1，但上下文仍留着 U1/A1，导致“看过 A1 后重答 U1”。

现在题目与上下文都从原始来源和 target_turn_index 派生：

```python
题目 = source_turns[target_turn_index]
上下文 = source_turns[:target_turn_index]
```

不一致的 `task_user` 或 `context_messages` 手工覆盖会被拒绝；修改展示用 `source_turns` 也会被拒绝。要改目标，就改目标位置，程序负责同时重建上下文。

只设置 approved=true 仍不够：必须填合法模式与位置。目标必须是已经有对应助手回答的用户消息。因此本例最后尚无回答的 U3 只能作为审核证据，不能直接选成回放题目。

### 4.4 模式仍然需要人判断

程序校验位置、角色和上下文边界，不能自动理解所有反馈语义。如果审核人把 U2 明确标成 original_task，程序无法仅凭文字证明这个判断错误。

这次解决的是**目标不明确和上下文错配**。任务性质与验收条件仍需要认真审核，不能批量盲目批准。

## 五、两个重叠窗口会不会重复评、互相泄漏

### 5.1 不会因为是两条日志，就分别安排成开发集和测试集

你之前的理解是：

```text
U1 A1 U2         → 开发集
U1 A1 U2 A2 U3   → 测试集
```

当前程序按会话 ID 做稳定哈希分组。同会话的窗口进入同一侧，不能这样拆分。

约 75% 的会话进入 `mutate_dev`，约 25% 进入 `promotion_test`。这是大样本期望，只有几个会话时不保证恰好 3:1，也不会为了凑数量强行拆同一个会话。

旧日志没有 session_id 时，需要人工填写一致的 group_id；新记录使用实际 session_id，不能靠修改 group_id 重分组。

**只有这一段对话时，没有独立测试会话，就不能晋级。** 可能执行开发侧检查和候选比较，但不会生成一份伪造的独立测试成绩。

### 5.2 两个窗口都选同一个 U1，只计一道题

程序按以下内容识别重复目标：

```text
会话归属 + 评测模式 + 目标请求内容 + 目标之前的上下文
```

如果两个窗口都选 U1，且上述内容相同：

- 验收条件相同：合并成一道题，`source_sample_ids` 保留多个来源。
- 验收条件不同：两条都暂停，标记 `conflicting_task_criteria`，需要统一标准。

不是简单地保留“更新的条件”就继续跑，也不会把同一题的重复出现当成更多成功样本。

去重基于保存内容的精确匹配，不是语义相似度去重。不同窗口缺失了不同的前文时，可能不会被识别为同一题，审核仍需关注上下文完整性。

### 5.3 重做 U1 和修正 U2 是两道不同的测试

这两者目标不同，可以同时存在，但仍属于同一会话、同一分组。

每条来源审核记录目前选择一个目标/模式。可以在不同来源记录中分别选择 U1 重做和 U2 修正；不要在审核文件里复制同一个 sample_id，重复 ID 会报错。

开发集和测试集需要覆盖相同的模式。不能用 original_task 的开发成绩，配 feedback_revision 的测试成绩完成晋级。报告保存 `scores_by_mode`，候选比较也检查各模式平均分不能下降。

## 六、验收标准从哪里来：不再让 C 给自己出题

### 6.1 人工给样本写验收条件

审核记录包含两类条件：

| 字段 | 执行者 | 适合判断什么 |
| --- | --- | --- |
| checks | 程序 | JSON 是否可解析、段落数、明确字符串是否出现 |
| requirements | 模型裁判 | 是否完成题目要求、内容是否符合给定事实和约束 |

它们由审核者针对任务填写，不再从当前 Skill C 的关键词自动推导。

对前面的 U1，可以设置：

```json
{
  "checks": [
    {"mode": "json_parseable"}
  ],
  "requirements": [
    "回答包含 summary 和 risks 两个字段，并分别给出总结与风险说明。",
    "risks 说明直接覆盖写入期间发生中断，可能导致配置文件不完整或损坏。"
  ]
}
```

这里 U1 本来就在询问覆盖写入风险，因此验收可以要求涵盖该风险。若 U3 新增了 U1 根本没有提供、模型也无法知道的私有事实，就不能把这条新增信息偷偷变成 U1 的必答条件。

### 6.2 作答模型和判分模型接收的内容不同

| 环节 | 收到的内容 |
| --- | --- |
| C 或 D 作答 | 对应 Skill 指令、目标请求、目标前上下文 |
| 程序检查 | 新回答、checks |
| 模型裁判 | 目标请求、目标前上下文、新回答、requirements 和 checks |
| 候选修改 | 当前 Skill 快照、开发题及验收条件、失败规则和判定原因 |

验收规则里的预期字符串不会直接发给作答模型，目标历史回答和后续反馈也不会直接发过去。反馈修正模式允许存在更早的历史回答，这是该题的有效上下文。

候选修改模型会看到开发侧验收条件，这是为了定位开发问题；测试侧题目与判分不送入本轮候选修改提示。

### 6.3 程序规则不负责理解所有语义

当前支持：

| mode | 参数 | 判断范围 |
| --- | --- | --- |
| json_parseable | 无 | 回答整体可被 Python JSON 解析器解析，不校验字段或 JSON Schema |
| max_paragraphs | max_paragraphs：正整数 | 按空行分段，段数不超过上限 |
| contains | text：非空字符串 | 区分大小写的字面子串包含 |
| not_contains | text：非空字符串 | 不包含指定字面子串 |

还有内置非空检查。每类可填写的 checks、requirements 各最多 12 条，至少填写一种。

这些检查用于明确格式约束，不代表“含有关键词就说明任务成功”。比如 JSON 可解析，不说明里面的风险分析正确。程序也不再因为 Skill 里出现“JSON”一词，就自动加上 JSON 硬规则。

## 七、当前 C、候选 D、冠军如何比较

### 7.1 先让 C 在开发题上重新作答

本例若选择重做 U1，生成新答案 `Answer_C(U1)`，按本题验收标准评分。

**评分对象是这个新答案，不是 A1，也不是 A2。** C 可能已经吸收用户纠错，所以历史 A1 失败不表示 C 现在也失败。

如果 C 在开发题上没有失败，不生成候选。整个流程不再天然导致“因为历史回答错了，所以必然产生 D”。

### 7.2 有开发失败，才尝试提出候选 D

修改模型看到当前 Skill 快照和最多前 4 条开发失败案例，尝试生成最多 2 个完整候选指令。完全相同的候选会去重。

生成 D 并不代表 D 更好。它只是待检验的修改建议，之后必须重新回答同一开发集。

C 来自线上互动中的提炼和维护；D 来自这次评测暴露的开发失败。它们的来源不同，但最终都表现为供作答模型使用的 Skill 指令。

### 7.3 候选先过开发比较，再看测试

程序先把 C 作为当前最佳版本。候选按顺序在相同开发题上生成新回答：

- 完整完成评测，样本 ID 一致。
- 没有硬规则失败。
- 平均分至少比当前选中版本高 0.05。
- 每种评测模式的平均分都不低于当前选中版本。

满足时替换选中版本。这里采用带最小改进幅度的顺序筛选，不是仅按最高分无条件排序。

### 7.4 测试阶段重新比较 C、选中版、已有冠军

样本数量和模式覆盖满足要求后：

```text
同一测试集 → 当前 C 重新作答
同一测试集 → 开发阶段选中的 D 重新作答
同一测试集 → 已有冠军 H 重新作答
```

旧冠军保存的历史成绩不参与分数比较。若两个版本在本轮构造出完全相同的请求，会使用本轮缓存，不重复调用模型；因此“重测”指采用本轮相同条件下的结果，不保证每个相同版本额外独立采样一次。

D 测试不通过时，保留已有冠军。本轮不会根据测试失败再去生成 D2 反复尝试。

### 7.5 当前默认晋级门槛

| 条件 | 默认值或要求 |
| --- | --- |
| 来源样本数量 | 至少 2 条，且有开发题与测试题 |
| 测试样本数量 | 至少 1 条，来自与开发侧不同的会话分组 |
| 模式覆盖 | 开发和测试覆盖相同评测模式 |
| 硬规则 | 选中版在开发和测试两侧均无失败 |
| 规则通过率 | 开发和测试两侧均至少 80% |
| 新候选相对 C | 测试平均分至少提高 0.05，各模式平均分不下降 |
| 相对已有冠军 | 同一测试集重测后至少提高 0.05，各模式平均分不下降 |
| 使用情况 | 至少 5 条计入的检索判定，相关率至少 35%，使用率至少 20%，未标记 pruned |

使用情况是额外的过程门槛，不证明任务正确。相关/使用判断也来自模型；非法布尔值、漏项、矛盾判定会被拒绝，无模型时不靠名称出现次数猜测。被拒绝的判定不计入这套统计。

没有已有冠军时，C 自己达到门槛也可以登记为初始冠军，这不代表已经证明性能提升。已有相同水平冠军时，不会仅因再次运行就重复晋级。

晋级结果写在独立的 `online-eval/champions/`，**不会自动覆盖当前活跃 Skill**。

## 八、分数怎么算：记住思路，再看公式

每个回答的每项检查产生通过或失败：

- 硬规则权重 2，包括非空检查与显式 checks。
- 模型语义要求权重 1。
- 通过获得该项权重，失败获得 0。

```text
单题分数 = 通过项权重之和 / 全部项权重之和
平均分 = 所有题目的单题分数平均值
规则通过率 = 通过判断数量 / 全部判断数量
```

例如一题有“非空、JSON 可解析”两项硬规则，加两项语义要求。总权重为 2+2+1+1=6；若只失败一项语义要求，单题分数为 5/6≈0.833，规则通过率为 3/4=75%。

平均分与规则通过率是不同指标。这个例子也说明，分数看起来较高，仍可能没达到通过率门槛。**规则通过率不是任务成功率。**

模型裁判每条要求必须返回唯一索引、真正的布尔 pass 和非空 reason。以下情况视为评测不完整，而不是伪造一个通过分数：

- 空答、网络异常、超时。
- 非法 JSON、漏判、重复索引、字符串 `"false"`。
- 输入过长、模型调用预算耗尽。
- REPL 使用的模型回调发现响应因长度等原因未正常结束。

合法返回 `pass=false` 表示该语义要求失败；格式错误表示不能可靠完成本轮评测，两者不同。

## 九、为什么这还不能叫独立泛化评测

假设 C 已经从 `U1 A1 U2 A2 U3` 学到了 JSON 输出规范，然后让它重答 U1。这能检查学到的规范是否在这个历史任务上体现出来，是有价值的回归检查。

但题目已经参与过 C 的学习，即使后来把日志划分成开发集和测试集，也不能改变这一点。

因此要区分：

1. **本轮候选修改隔离：**D 的修改提示只用开发失败，不用测试题。
2. **从未参与学习的独立任务：**C、D 的学习和修改过程都没有使用这些任务。

当前会话分组实现了第一层的流程约束，不自动保证第二层。反复查看同一测试集的结果后人工修改，也会逐渐形成间接过拟合。

还有两个限制：

- `/skill-eval` 当前比较 C 与这次候选 D，不自动加载历史 A/B 做演化前后的完整消融。
- 使用的是文本 side_query，没有实际运行 shell、文件编辑、MCP 等完整工具链。它不能证明真实代码修复成功。

正式对外报告自进化收益，需要另建未参与学习的任务集，冻结版本、模型和参数，保存完整逐题结果，进行人工抽检和多次运行。

## 十、Replay 越来越多，会不会全部反复调用模型

### 10.1 进入模型评测的数量有上限

| 项目 | 默认上限 | 作用范围 |
| --- | --- | --- |
| 保留来源池 | 最近 200 条 | 每个 Skill |
| 本轮选题 | 24 条 | 每个 Skill |
| 每会话选题 | 2 条 | 每个 Skill 的本轮样本 |
| 候选版本 | 2 个 | 每个 Skill |
| 模型调用 | 80 次 | 一次命令中全部 Skill 共享 |
| 单请求输入 | 24000 字符 | system 与 user 合计 |
| 单调用超时 | 60 秒 | 每次模型调用 |

程序从已审核题目中交替选开发侧与测试侧，避免开发题把测试题全挤掉。不是把所有来源逐题调用模型。

例如本轮 6 道开发题、2 道测试题，存在语义要求，产生一个候选且需要重测不同的旧冠军：C 开发约 12 次调用、候选生成 1 次、D 开发约 12 次，测试三版本约 12 次，总计约 37 次。这是流程示意，不是费用实测；没有语义要求或出现缓存命中时会更少，异常则可能提前中止。

### 10.2 缓存只在本轮有效

相同 system/user 请求在同一轮复用结果，包括相同的作答或判分请求；下一次运行重新建立缓存。已入选题目可能再次被评测，本实现不是“每条题终身只测一次”的增量评测系统。

原始日志仍会被读取、整理，历史审核记录也继续保存。**模型调用有上限，不代表磁盘读取量和所有审计文件大小都有固定上限。** 大规模使用后仍需日志归档和索引优化。

### 10.3 长 Skill 不默默截断

请求超过 24000 字符时，明确返回 `request_too_large`，本轮不能晋级。不会只截取 Skill 前半部分，再假装完整测过。

这个限制也适用于候选修改和裁判请求。可以整理必要上下文、改善 Skill 结构，或通过 Python 参数显式调整限制；本次审核机制不允许直接伪造精简后的来源消息。

字符上限不是 token 上限，调用次数也不是精确金额上限；SDK 内部重试可能增加实际网络请求与费用。默认 REPL 的辅助请求输出上限是 2400 tokens，过长候选可能因截断被拒绝。

## 十一、实际怎么操作

### 第一步：生成待审核清单

在项目根目录启动 mawoagent，输入：

```text
/skill-eval
```

命令先等待已调度的后台任务结束，再读取来源与活跃 Skill。初次没有已批准样本时，通常显示 `review_required`，不会对未批准样本调用评测模型；等待中的既有后台任务可能继续自己的模型调用。

命令会输出 `review_file` 路径。打开对应的 `replay_review.jsonl`。

### 第二步：看 source_turns，绑定目标并填标准

针对本例重做 U1，下面是便于阅读的 JSON 对象示意。实际 JSONL 文件必须一条记录一行；编辑生成的原记录，保留它的 sample_id、source_hash、source_turns，不要用示意值替换真实 ID。

```json
{
  "review_schema": 3,
  "sample_id": "保留生成的原值",
  "source_hash": "保留生成的原值",
  "approved": true,
  "reviewed_by": "审核者名字",
  "text_only": true,
  "group_id": "来源会话ID",
  "evaluation_mode": "original_task",
  "target_turn_index": 0,
  "feedback_parent_turn_index": null,
  "requirements": [
    "回答包含 summary 和 risks 两个字段，并分别给出总结与风险说明。",
    "risks 说明直接覆盖写入期间发生中断，可能导致配置文件不完整或损坏。"
  ],
  "checks": [
    {"mode": "json_parseable"}
  ]
}
```

如果改为本例的反馈修正：

```json
{
  "evaluation_mode": "feedback_revision",
  "target_turn_index": 2,
  "feedback_parent_turn_index": 0
}
```

这是修改三个字段的示意，不是另一条完整 JSONL 记录。验收条件也要重新检查是否适用于 U2。

`text_only=true` 表示你确认现有输入足够完成任务，不需要真实工具。不能为了让样本进入评测而随意批准。

### 第三步：再次运行 /skill-eval

根据状态判断接下来做什么：

| 状态 | 含义与下一步 |
| --- | --- |
| review_required | 没有可用的已审核样本；检查审核字段和 review_queue |
| incubating | 没有开发题、样本不足、缺少独立测试题或模式不匹配；补充有效来源 |
| unobserved | 有样本，但没有可用模型回调或活跃 Skill，未进行配对生成 |
| incomplete | 本轮调用或判分失败；查看具体错误，不能把部分结果当通过 |
| watch | 已完成比较，但质量、改进幅度或使用情况门槛未通过 |
| healthy | 本轮满足冠军登记条件；默认写入独立冠军产物 |

不要为了让状态变为 healthy，把同会话改成不同 group_id，或把模型报错当作答对。

审核文件损坏、常见文件读写错误会显示错误并返回 REPL，不自动清空审核文件。旧审核模式升级时，原记录保存在 `previous_review`，新记录取消批准，要求重新选择轮次。

来源内容变化造成 source_hash 不一致时，先核对新的证据与目标，再更新审核；不能只为消除报错盲目替换哈希。

### 第四步：查看逐题证据

```text
.mawoagent/skill-evolution/
├── online_provenance.jsonl
├── online_skill_provenance.json
├── online_eval_report.json
└── online-eval/
    ├── datasets/<lineage>/
    │   ├── replay_pool_v2.jsonl
    │   ├── replay_review.jsonl
    │   ├── review_queue.jsonl
    │   └── selected_replay.jsonl
    ├── runs/<lineage>/<run>/
    │   ├── replay.jsonl
    │   ├── outputs.jsonl
    │   ├── judgments.jsonl
    │   └── summary.json
    ├── champions.json
    └── champions/<lineage>/
        ├── champion.json
        └── SKILL.md
```

- `replay.jsonl`：本轮实际选择的题目、上下文、模式、分组和验收条件。
- `outputs.jsonl`：各版本重新生成的回答，通过 sample_id、variant_id 对齐。
- `judgments.jsonl`：每项规则的通过/失败，语义条件带裁判理由。
- `summary.json`：版本快照、开发与测试成绩、各模式成绩、候选和晋级/中止原因。
- `online_eval_report.json`：整体状态、实际调用次数、预算配置和阈值。

所谓冻结落盘，是保存本轮用过的输入与输出供追查，不表示来源池永远不变、以后每轮都必须测全部历史题。文件本身也不是不可篡改的存储。

### 可选：通过 Python 调整预算

下面片段放在已有 Agent 实例的异步运行环境中执行：

```python
from agents.online_skill_eval import evaluate_online_skill_evolution_async

report = await evaluate_online_skill_evolution_async(
    side_query=agent._build_side_query(max_tokens=2400, require_complete=True),
    replay_limit=12,
    pool_limit=200,
    max_candidates=1,
    max_calls=40,
    max_request_chars=24000,
    timeout=60,

```

只有未批准样本时不会调用评测模型。若想同时不写报告和产物，需设置 `write_report=False`、`write_artifacts=False`；只关闭写文件不等于禁止模型调用。自定义 side_query 应自行拒绝供应商返回的截断结果，字符串接口不能自动看见响应的 finish_reason。

## 十二、你之前的问题逐项对应到现在

| 原来的疑问 | 当前实现 |
| --- | --- |
| Replay 是否直接从日志提取 U/A？ | 先提取来源证据，再人工绑定目标轮次，生成明确题目 |
| U2 明明是反馈，为什么让它回答 U2？ | 只有明确选择反馈修正时才这样评；重做原题则选 U1 |
| 怎么知道检查的是 A1 还是 A2？ | 不把历史 A1/A2 当基线，检查各版本针对绑定目标新生成的答案 |
| 用 C 的规则查它学习之前的回答，会不会必然失败？ | 标准来自样本审核；先让 C 重答，有开发失败才提出候选 |
| 两个窗口重复，怎么分开发和测试？ | 同会话同组；相同目标去重，没有独立测试组就不晋级 |
| 程序关键词规则能覆盖所有情况吗？ | 不能；只执行显式格式检查，语义条件单独判分 |
| D 与自进化得到的 C 有什么区别？ | C 是当前活跃快照；D 是针对开发失败提出、尚未部署的实验版本 |
| Skill 特别长怎么办？ | 超过输入上限明确中止，不静默截断 |
| Replay 越来越多怎么办？ | 来源池、入选题数和模型调用均有限制；原日志归档仍需另做 |
| 模型裁判幻觉怎么办？ | 格式严格校验、异常不晋级、保存逐题证据；事实误判仍需人工抽检或外部验证 |

## 十三、面试时怎么讲，哪些内容不用死背

可以先用这一段说明主要思路：

> 我把真实对话先保存成来源证据，再确认评测目标和验收条件。针对连续纠错，区分原任务重做与反馈修正：重做 U1 时排除 A1 和后续反馈；修正 U2 时保留 U1/A1，排除 A2。当前 Skill 和候选使用同一输入重新作答，开发题用于修改，按会话隔离的测试题用于比较，旧冠军也重新测。明确格式由程序检查，语义由模型判分；异常不能晋级，候选不会直接覆盖活跃 Skill。样本和调用有预算，逐题输入输出都保存下来，便于核查。

如果面试官追问可靠性，再补充：

> 模型裁判不是绝对正确的，严格 JSON 校验只能解决格式问题，不能消除事实误判。我会用人工抽检核对判定，对可验证任务补充确定性验证。来源对话可能已参与 Skill 学习，所以当前成绩是回归检查；证明泛化提升，需要另一套未参与学习的任务和重复实验。

不用死记 0.05、80% 等配置值。优先讲清楚四件事：

1. **测什么：**选定目标轮次，避免把反馈与原任务混淆。
2. **如何比较：**相同输入、相同标准、各版本重新作答。
3. **怎样隔离：**同会话同组，开发用于修改，测试用于验证。
4. **什么时候拒绝：**缺少独立样本、硬规则失败、无明确改进或评测异常时不晋级。

当前没有实现完整工具执行评测、多裁判一致性判定、自动外部事实核查或统计显著性分析，面试时不要把这些后续方向描述成已有能力。
