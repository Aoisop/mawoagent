# 项目评测：自进化和会话折叠到底怎样评

这份文档先讲**实验思路**，再说明 mawoagent 现在的代码做到了哪一步。两件事要分开看：

| 要评的能力 | 核心问题 | 最直接的比较 |
| --- | --- | --- |
| Skills 自进化 | 新学到的 Skill 是否真的让代理更会完成同类任务？ | 同一批任务，使用旧 Skill 与新 Skill 分别作答，比较成功率和错误 |
| 会话折叠 | 对话很长时，把历史压成记忆是否有助于继续完成任务？ | 同一批长任务，仅改变“是否允许折叠”，比较最终答案、成本和失败原因 |

**关键原则：**要判断某项机制是否有用，先固定题目、模型、工具和预算，只改变这一项机制，再按同一标准判分。程序里“能生成 Skill”或“能保存折叠记忆”，只能证明功能可运行，不能证明它提升了结果。

## 一、自进化评测：先理解要比较什么

### 1. 自进化是怎样发生的

假设用户连续几次要求“回答事实问题时给出可核查来源”。代理第一次漏了来源，下一轮用户指出了这个问题。mawoagent 会从对话和反馈中提炼经验，形成或更新一个 Skill，例如“回答事实问题时附来源”。以后遇到类似问题，代理检索并使用这个 Skill。

因此，自进化有三个不同的问题：

1. **学到了吗？** 有没有从对话中提取并保存合适的 Skill；错误反馈有没有被转化为正确规则。
2. **用上了吗？** 相似请求来时，Skill 有没有被检索到、是否相关、回复是否实际遵守它。
3. **有帮助吗？** 使用新 Skill 后，任务结果是否比旧版本更好，且没有在其他任务上退步。

前两项是过程指标，第三项才是效果指标。把“创建了 10 个 Skill”当成“能力提升了 10 次”，或把“规则通过率”直接叫“任务成功率”，都会混淆这三层。

### 2. 当前 mawoagent 的 `/skill-eval` 实际怎样做

当前实现是**经人工确认任务与标准的文本回放比较**。详细操作见 [在线 Skills 评测实现说明](在线Skills评测实现说明.md)。

```text
原请求 + 请求前上下文 + 原回答 + 下一轮消息
    ↓ 人工确认原任务和验收条件；下一轮消息不自动视为反馈
按会话 ID 固定划分开发集和测试集
    ↓
当前 Skill 重新回答开发题，按样本验收条件评分
    ↓ 有失败才生成最多两个候选，候选只使用开发集信息
候选重答同一开发集，选择更好的版本
    ↓
当前版、选中版、已有冠军重答同一测试集
    ↓
通过质量与使用门槛后，保存独立冠军快照
```

代码入口是 `agents/main.py` 的 `/skill-eval`，主要流程在 `agents/online_skill_eval.py`。首次运行生成 `replay_review.jsonl` 待复核清单，未批准的样本不调用模型。对 `U1 A1 U2`，新记录明确保留 U1 为原请求、A1 为原回答、U2 为下一轮消息；必须明确选择 original_task 或 feedback_revision，并绑定 source_turns 内的目标用户消息 index；反馈模式还需绑定更早的原请求。题目及上下文由来源自动重建，不能直接改写 task_user。旧审核须重新确认，不自动沿用。

正式作答只收到版本 Skill、选定用户消息和它之前的上下文；目标回答、后续反馈和验收规则不发送给作答模型。反馈修正模式会保留更早的原回答。重复窗口指向同一任务时去重，验收条件冲突则暂停；两种模式分项统计，不能互相替代测试。当前版本与候选都重新生成，不再把旧 A1 当作当前版本的成绩。需要工具的任务不能按纯文本任务批准。

### 3. 样本、指标和晋升门槛是什么意思

- **来源和分组：**来源为在线日志、索引和已有样本池。按会话 ID 的稳定哈希约 75% 分开发集、25% 分测试集；同会话重叠窗口不能跨集。旧日志缺少会话 ID 时需要人工补充分组。没有独立测试会话则不晋级。
- **验收条件：**由样本复核者填写，不再从 Skill 关键词自动生成。明确声明的 JSON 解析、段落数、字面包含/排除由程序检查；语义要求交给模型判定。语法可解析或存在字符串不代表事实正确。
- **计分：**硬规则每项权重 2，语义条件每项权重 1。每题先除以总权重得到 0～1 分，再取题目平均。规则通过率不等于任务成功率。模型判分返回格式错误、空答、超时或预算耗尽时记录 incomplete，不晋级。
- **选择：**候选在同一开发集至少提高 0.05 且无硬规则失败才被选中。选中候选还要在相同测试题上比当前版提高至少 0.05；已有冠军时也必须超过本轮重测的冠军至少 0.05，历史分数不参与比较。
- **门槛：**默认至少 2 条样本、1 条独立会话测试题，开发与测试集均无硬规则失败且规则通过率至少 80%；另要求检索至少 5 次、相关率至少 35%、使用率至少 20%、未被标记为 pruned。这些是内部筛选门槛。
- **费用控制：**每个 Skill 保留最近 200 条来源、每轮最多 24 条、每会话最多 2 条、候选最多 2 个；整次评测最多 80 次模型调用。长输入超过字符上限会中止，不默默截断。

**来源对话可能已经参与当前 Skill 学习，所以这些分数只能作为回归检查。** 会话分组能隔离本轮候选修改，不能把学习过的题变成未见任务，也不能消除模型裁判误判。

### 4. 真正验证“自进化有帮助”，实验应该怎么做

用**同一批从未参与 Skill 生成和修改的任务**做成对实验。比如 50 个需要来源的事实问答，每题运行两次：A 用更新前的 Skill，B 用更新后的 Skill。两次使用相同模型、工具、提示、最大轮数、随机种子与判分器；随机化 A/B 的执行顺序，每题建立独立会话，防止前一题影响后一题。

对每题分别记录“答案是否正确、来源能否支持答案、是否遵守格式、是否超时、用了多少 token/工具调用”。可设置**硬门槛**：编造来源即使格式漂亮也判失败。主指标可定义为 `任务成功率 = 成功题数 / 固定题目总数`；再列出“仅新版成功、仅旧版成功、两版都成功、两版都失败”的题数，分析新 Skill 带来的收益和退步。先用一批开发题迭代 Skill，最后只在未见过的测试题上报告结果；测试题不能反过来指导修改。

这一步目前**没有完整的 mawoagent 端到端 A/B 评测入口**。如果要实施，需要一个评测脚本冻结任务清单，分别加载旧/新 Skill 快照，让完整 agent 运行并保存逐题轨迹。当前 `/skill-eval` 的 `outputs.jsonl`、`judgments.jsonl`、`summary.json` 可以用来检查规则质检，但不能替代完整代理运行的逐题结果。

## 二、折叠评测：到底在验证什么

### 1. 折叠解决的是什么问题

长任务会积累用户对话、工具输出、失败尝试和中间决定。历史太长时，模型可能超出上下文窗口，或者反复重试已经失败的路径。折叠的想法是把旧历史压成一份**足够继续工作的状态**：

- **事件记忆 `episode_memory`：**原始目标、已经做过的关键步骤、结果。
- **工作记忆 `working_memory`：**当前子目标、尚未解决的问题、下一步。
- **工具记忆 `tool_memory`：**用过什么工具、有效参数、常见错误和经验。

例如代理为一个代码问题已经读了十几个文件、试了三次失败的命令。理想的折叠后记忆会保留“用户要修什么、改过哪些文件、哪个测试仍失败、下一步查哪里”，但可以丢弃大量重复工具输出。若摘要漏了关键路径或把失败说成成功，折叠反而会伤害结果。所以要评的不只是“压缩了多少 token”，还要评**完成任务是否更好，以及丢失了什么信息**。

mawoagent 的实现见 [`agents/agent.py`](agents/agent.py) 和 [`agents/session_memory.py`](agents/session_memory.py)：完整折叠可由 `/compact`、`compact_context` 工具或上下文超过有效窗口 70% 触发；辅助模型生成上述 JSON，失败时保留一段原文作为回退，然后用记忆替换旧对话。另有工具结果截断、60% 以后清理过期结果、空闲后的微压缩。这些是不同压缩层，做消融时必须说明究竟关闭哪一层。折叠事件会记在 `.mawoagent/sessions/<session-id>.folded-memory.jsonl`。

### 2. 折叠的对照实验怎么设计

把同一批**足够长、确实可能触发折叠**的任务分成两个条件：

| 条件 | 运行方式 |
| --- | --- |
| A：允许折叠 | 保持 mawoagent 当前折叠逻辑；记录触发时机、记忆内容和折叠开销 |
| B：禁止完整折叠 | 阻止自动折叠、`/compact` 和 `compact_context` 真正替换历史；其他配置与 A 相同 |

第一轮只比较“**有无完整结构化折叠**”，两组仍使用相同的工具输出截断、snip 和微压缩策略，这样差异才主要来自折叠。若想评价“整个压缩系统”，再单独做第二组实验。当前 `agents/eval_folding.py` 使用 `Agent(enable_folding=False)` 同时关闭自动折叠、手动折叠和 `compact_context`，不能只关自动阈值，因为代理仍可能调用工具折叠。

每道题先固定题目 ID 和标准答案，再用两组各运行一次，模型、温度、工具、网络环境、权限、最大轮数、时间/token 预算都相同。标准答案只供判分器使用。每题新会话，避免其他题的记忆、文件改动或缓存进入本题。无折叠组可能更早碰到上下文上限，这也是实验结果的一部分；要把“上下文溢出/超时/空答”算进预定分母，而不是删除。

最后看三类结果：

1. **最终能力：**一次运行的最终答案是否正确，成功率 `= 答对题数 / 预先固定的总题数`；长任务可再看是否完成、是否达成用户约束。
2. **代价：**每题的输入/输出 token、折叠辅助模型 token、费用、耗时和工具调用数。折叠可能提高成功率，也可能额外消耗模型调用。
3. **机制原因：**对齐每题 A/B 轨迹，数“仅折叠组答对”和“仅无折叠组答对”；查看折叠前历史与折叠后记忆，判断关键事实是否被保留、错误路径是否被打断。只报一个总分解释不了作用机制。

建议每题保存 `task_id、condition、配置/代码版本、原始输出、提取答案、标准答案、判分结果、失败类型、token、费用、折叠次数、每次折叠的记忆和完整轨迹路径`。最终报告包含固定题目列表、两组逐题记录、判分脚本、总体与子类结果；若有随机性，按多个种子重复，并给出波动范围。

## 三、现在能直接看什么，下一步缺什么

在项目根目录、配置好模型后，可以按 [`README.md`](README.md) 启动 REPL：

```bash
python3 -m agents.main
```

输入 `/skill-eval` 可查看**现有的 Skills 回放质检**。原始来源和评测产物位于 `.mawoagent/skill-evolution/`；重点看 `online-eval/datasets/*/replay_review.jsonl`、`selected_replay.jsonl`、`online-eval/runs/*/*/outputs.jsonl`、`judgments.jsonl`、`summary.json`。这条命令先生成待复核任务；有已批准样本时会调用模型、写产物，并可能更新独立保存的本地 champion，不覆盖活跃 Skill。折叠则可在长会话中通过 `/compact` 或 `compact_context` 观察；检查 `.mawoagent/sessions/*.folded-memory.jsonl` 能看到实际记忆，但看不到“无折叠时同题会怎样”。

### 现在新增的折叠实验入口

`agents/eval_folding.py` 会把同一题分别以 `fold_on`、`fold_off` 运行，交替执行顺序，保存逐题轨迹及配对汇总。先用不调用模型的校验命令检查案例格式：

```bash
python3 -m agents.eval_folding --cases data/folding_eval_smoke.jsonl --output .mawoagent/folding-eval/smoke-001 --validate-only
```

配置好 `.env` 后，可运行一个**只验证管线的合成样例**：

```bash
python3 -m agents.eval_folding --cases data/folding_eval_smoke.jsonl --output .mawoagent/folding-eval/smoke-001 --fold-after-turn 2 --max-turns 10
```

这会在第三轮提问前让 `fold_on` 组安排一次折叠，`fold_off` 组保留原历史。`--fold-after-turn` 仅是让短样例确实发生折叠的本项目实验控制，并非 DeepAgent 原始触发方式。评测入口默认分别并行生成事件、工作、工具三类记忆，单题最多折叠 3 次；对应 `--fold-memory-mode three_parallel` 与 `--max-fold-limit 3`。也可用 `single_json` 与不同上限做本项目内部对照。`--output` 必须是尚不存在的目录；命令会真实调用模型，产生费用。若不传 `--fold-after-turn`，就使用生产环境的自动阈值和模型主动工具触发；可用 `--fold-threshold 0.5` 改变自动阈值。运行后查看 `summary.json` 的 `cases_with_fold`：如果为 0，就不能把这次结果解释为折叠效果。

正式题目可提供 JSONL，每行至少有 `id`、`prompt`、`answer`；多轮任务可用 `prompts` 数组。对从 GAIA/HLE 挑选的题目，应逐题审核所需工具并写入 `required_tools`（无需工具时为 `[]`）；未审核的原始数据仍可校验和试跑，但不计入有效消融配对。程序还识别 GAIA 的 `task_id`、`Question`、`file_name` 和 HLE 的 `question`，但当前默认只开放本地只读工具，评分是精确、规范化字符串或纯数字匹配，**不是论文官方 GAIA/HLE 判分**。非文本附件、图像及声明需要不可用工具的题目会在模型调用前被拒绝。建议先用 `--text-only --limit N --validate-only` 审核题目，再确定联网工具和正式判分器是否齐全。结果目录包含 `config.json`、`results.jsonl`、`summary.json`、`review_queue.jsonl`，每题两组另有 `trace.json` 与 `console.log`；开启组的 `trace.json` 还保存每次折叠前的 transcript。`summary.json` 的准确率仅使用两组都完成、开启组实际折叠、关闭组未折叠且工具需求已审核的配对；其他配对会列出无效原因。`main_*_tokens` 是主模型，`side_*_tokens` 包含辅助模型折叠调用；`--max-cost` 仅按代码中的统一单价估算，不是账单价格。

仍需补齐的是正式 benchmark 环境与判分器，以及自进化旧/新 Skill 的端到端 A/B 脚本。现有 `/skill-eval` 提供 Skills 回放质检；新入口提供折叠对照的运行与记录；论文提供实验设计与参考数字，三者应分别标注。
